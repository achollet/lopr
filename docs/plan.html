# Local Pull Request

## Pitch

Outil pour creer un pull request 100% localement, sans repo distant, afin de reviever le code produit par un agent IA : commentaires par ligne, threads, request changes ou approbation, puis merge. Reproduit le workflow PR GitHub en local, en boucle avec l'agent (local ou SaaS). Stack retenue : TypeScript monorepo (core + CLI + TUI ink + extension VS Code).

## Fonctionnalites

- diff local (git diff merge-base...head, trois-points, meme semantique que GitHub)
- commentaires ancres par ligne : (sha, fichier, ligne) + re-ancrage contextuel en secours
- threads + resolution
- statuts de review : comment / approve / request-changes
- merge --no-ff dans la branche de base
- export REVIEW.md (ou skill opencode apply-review) pour que l'agent ingere les retours

## Questions ouvertes

- surface de review principale : VS Code (webview) ou TUI ?
- nom du produit (lopr ? local-pr ?)
- multi-reviewer ou solo strict ?
- partage entre machines (remote local) ?
- detailler le moteur d'ancrage — c'est le coeur du logiciel


- Toutes resolues — voir Decisions (grille).

## Decisions (grille)

- Surfaces: core identique, presentations differenciees; features peuvent diverger entre TUI et extension. VS Code webview = surface principale, TUI = minimum (diff/merge/export).\n- Reviewers: solo strict en V1; stockage ouvert a un champ author futur, pas de design ferme.\n- Partage: pas de partage actif en V1; store portable par fichiers.

- Unite de revue: la boucle entiere. Les commentaires persistent et se re-ancrent a travers les iterations agent (implementation/feedback jusqu'a version satisfaisante). Re-anchorage = coeur dur.

- Stockage: JSON par review; rendu uniquement via les surfaces (TUI/extension), pas de lecture directe du fichier par l'humain.\n- Export: REVIEW.md agnostique de l'agent, contrat stable. Skill apply-review dans le repo; son installation fait partie de l'installation du TUI/extension, vers un emplacement defini par l'utilisateur.\n- Merge: merge dans main, conflits regles automatiquement puis commit. Deux modes: (a) repo distant -> push de la branche + ouverture d'une PR (si repo multi-collaborateur); (b) 100% local mono-contributeur -> merge branche dans main, suppression branche et du fichier de review.\n- Nom: lopr (binaire/package), nom complet 'Local Pull Request'.

- Ancrage: cote nouveau, commentaire = (file, line) courant + (oldSha, oldLine) origine; ligne seule en v1, endLine nullable.\n- Re-anchorage: (a) mapping par hunks git diff oldHead..newHead exact, puis (b) recherche contextuelle tolerant aux espaces si la ligne tombe dans une zone reecrite, puis (c) etat detache.\n- Echec d'ancrage: detache, jamais silencieux, jamais bloquant seul; figure dans REVIEW.md section 'non localises'; le reviewer re-ancre ou ecarte au merge.\n- Mode: 100% local uniquement, pas de mode PR distant. Merge: avertir l'utilisateur et demander son accord avant de merger; si refus, l'utilisateur gere la branche lui-meme, la PR locale peut quand meme etre marquee terminee.\n- Conflits: main gagne (contenu de main privilegie sur les chevauchements), puis relance d'une boucle pour reappliquer le besoin contre le nouveau main; conflits auto-resolus journalises dans la revue.

- Statuts PR: open, request-changes, approved, merged, done (terminable sans merge, atteignable de partout), closed. Transitions validees par le core. Statuts de review par review, pas par commentaire.\n- Commentaire: id, file, line courant, oldSha/oldLine, instantane de contexte (lignes voisines, obligatoire pour le fallback Q10), body, status (active/resolu/detache), auteur reserve, parentId + resolvedAt. SUGGESTION DE CODE OBLIGATOIRE EN V1: proposer un patch inline 'remplacer X par Y' — un des buts de l'appli.\n- Diff: renames detectes (defaut git), gros fichiers tronques + extension dans la surface, fichiers generes ignores par patron configurable (lopr.ignore), binaires marques et jamais aneres.\n- Skill: lopr skill install [--path], defaut interactif, verif a la premiere execution, config retient le chemin + reinstallation proposee.\n- Delivery: pnpm + tsup + vitest, version unique pour les 4 packages, extension en .vsix. Repo GitHub + CI/CD GitHub Actions a concevoir, extension trouvable depuis VS Code a etudier.

- Branche de base: defaut dans .lopr/config.json du repo, surchargeable par parametre CLI de lopr, fallback sur la branche par defaut git.\n- Repo: GitHub public, licence MIT; dans un premier temps, PR et contributions limitees aux contributeurs (l'utilisateur).\n- Extension: .vsix seul attache aux releases jusqu'a la v1.0; marketplace VS Code et Open VSX a etudier a la v1.0.

- Repo workflow: trunk-based (branches courtes par boucle agent, revue via lopr, merge dans main toujours releasable); conventional commits imposes en CI (commitlint); release notes auto-generees depuis les titres de PR a chaque tag v*.\n- Contrat REVIEW.md: en-tete (branche/base, statut), section conflits auto-resolus (main gagnant), commentaires par path:ligne (extrait, retour, suggestion optionnelle), section non localises (detaches).

Analysis

An AI agent produces code quickly — too quickly to eyeball. Reviewing it the GitHub way (three-dot diff, line comments, threads, approve/request-changes, merge) requires a remote repository that may not exist, and that nobody else needs. The unit of review is the whole agent loop: implement → review → feedback → re-implement, possibly several times, until the result is satisfactory. The hard problem is that comments written on iteration N must still mean something on iteration N+1, when the code moved — hence line anchors that persist and re-anchor across iterations.

  • Single human reviewer, solo. No multi-user, no remote PR mode in V1. The store stays portable by plain files, with an author field reserved for the future.
  • Local first. Everything runs against the working repo's git history; merge is a local --no-ff into the base branch, warned first and never forced.
  • Two surfaces, one core. The VS Code webview is the main review surface; the TUI is the minimum viable one (diff / merge / export). Features may diverge per surface, the domain logic does not.
  • Agent feedback loop is a first-class output. REVIEW.md is a stable, agent-agnostic contract ingested via the apply-review skill.

Architecture

TypeScript monorepo, pnpm workspaces. Four packages, one shared version:

packageresponsibility
coreDomain only: diff model, review/comment model, status state machine, anchoring & re-anchoring engine, storage (JSON per review), merge orchestrator, REVIEW.md exporter. No I/O except through injected adapters.
cliThe lopr binary. Thin wrapper over core: commands new · comment · approve · request-changes · resolve · status · merge · export · skill. Reads .lopr/config.json for the base branch, CLI flag overrides, git default fallback.
tuiInk TUI, three panes (files / diff / threads), keyboard-driven. Minimal surface: diff, comment, status, merge, export.
vscodeVS Code extension, webview review surface. Extension host talks to the webview over the standard message protocol; both load core.

Key components in core:

  • GitGateway (interface) — shells out to the system git. Implementations are tested against throwaway repos in vitest. Diff via git diff --merge-base base head (three-dot, the semantics GitHub PRs show: stable when the base moves, Git 2.30+). Rename detection on by default; generated files filtered by configurable lopr.ignore; binaries marked and never anchored.
  • Anchoring engine (the core of the software) — a comment carries its current (file, line) plus its origin (oldSha, oldLine), with a mandatory instant snapshot of surrounding lines for the fallback. Re-anchor order: (a) exact hunk mapping over oldHead..newHead, (b) whitespace-tolerant context search when the line sits in a rewritten zone, (c) detached state — never silent, never blocking alone.
  • Status state machine — PR: open → request-changes → approved → merged, plus done (terminable without merge, reachable from anywhere) and closed. Review status is per review, not per comment. Transitions validated by core.
  • Comment model — id, file, line, oldSha/oldLine, context, body, status (active/resolved/detached), author, parentId, resolvedAt. Inline code suggestions (replace X by Y) are a mandatory V1 capability.
  • Storage — one JSON file per review. Humans never read it; surfaces render it.
  • Merge orchestrator — --no-ff into the base branch, user consent first; conflicts auto-resolved main-wins, each auto-resolution journalised in the review, then the loop re-runs to re-apply the need against the new base.
  • REVIEW.md exporter — header (branch/base, status), auto-resolved conflicts section, comments by path:line (snippet, feedback, optional suggestion), and a non localized section for detached comments.

Chosen stack

  • TypeScript + pnpm workspaces. One language across CLI (Node) and the VS Code extension (runs in the extension host, also Node) — a second toolchain would buy nothing here. pnpm gives strict, fast workspaces and a single version across the four packages.
  • tsup for bundling (ESM, fast, zero-config for CLI and extension out).
  • vitest for the unit tests that carry the value: the anchoring engine, diff parsing, status transitions, merge conflict resolution — all pure enough to test without a UI.
  • Ink for the TUI (React renderer, @inkjs/ui widgets, ink-testing-library for in-memory rendering) — the ecosystem standard, proven for three-pane review UIs; see knowledge base ink-tui.
  • git via child_process, not libgit2 — matching "100% local, same semantics as GitHub" (--merge-base three-dot, rename detection, --no-ff) with the user's own git.
  • VS Code webview for the main surface; extension shipped as .vsix attached to releases until v1.0, marketplace/Open VSX studied at v1.0.

Risks

  • Re-anchoring fidelity — a rewritten zone can mis-anchor a comment. Mitigation: hunk-exact mapping first, whitespace-tolerant context search second, explicit detached state third; a detached comment is surfaced, never silently dropped, and re-anchored or discarded at merge.
  • Git semantics drift — rename detection, ignored generated files, truncated large files can make the local diff disagree with what a reviewer expects. Mitigation: lopr.ignore, binary marking, truncation with an explicit notice in the surface.
  • Auto-resolving conflicts main-wins can lose intent. Mitigation: journalise every auto-resolution in the review, and re-run the loop to re-apply the need against the new base.
  • Webview development cost — the extension is the largest surface. Mitigation: the TUI is the minimal fallback, and both share the same core; dogfooding lopr on its own trunk-based branches.
  • Single-version releases — four packages released in lockstep needs CI discipline (commitlint, release notes from PR titles, tags). Mitigation: defined in the repo workflow from day one.
