Git gateway

The three-dot diff in core, with the same semantic as a GitHub PR. The unit of review here is the commit range: merge-base(base, head)..head.

Files: packages/core/src/{gateway,diff,config,ignore,types}.ts + diff.test.ts (tests run against throwaway real git repos via test-utils.ts).

Decisions taken:

  • git via child_process, no libgit2. GitGateway interface + GitCli impl; --merge-base form of the three-dot diff (Git 2.30+), the exact semantics GitHub PRs show.
  • Three git calls per diff, run in parallel: --name-status -z (statuses + paths), --numstat -z (additions/deletions, binary detection via -\t-), full unified diff (per-file bodies). Bodies are correlated to entries positionally: all three come from the same git diff machinery (path-sorted), and a length mismatch throws rather than silently misattributing.
  • Renames/copies (-M, git default threshold) carry oldPath; numstat reports the new path, so stats map by new path.
  • lopr.ignore = glob patterns in .lopr/config.json ({"ignore": ["**/dist/**"]}), matched with minimatch (dot: true). The base field lives in the same file; resolution order: CLI/option → config → git default branch (main/master) → clear error.
  • Binary files: binary: true, zero add/del counts, body kept (they will never be anchored later).
  • Traps hit: vitest root include is cwd-relative — switched to **/*.test.ts so a per-package vitest run finds its own tests; git symbolic-ref --short -q HEAD falls back to HEAD for detached state; maxBuffer raised to 64 MiB for large agent-loop diffs.

Diff model

Parsing of the per-file unified diff body into hunks, in packages/core/src/diff-model.ts.

Decisions taken:

  • parseDiffBody is pure and always returns every hunk. Truncation is a display concern (truncateHunks(hunks, max)), never part of the model the anchoring engine will read — a truncated map would silently lose comment re-anchors.
  • Hunk line numbers are tracked incrementally from oldStart/newStart: context increments both, removed only old, added only new. The \ No newline at end of file marker is ignored (it is not a diff line). Omitted counts in @@ -5 +5 @@ mean 1. Section headings after the second @@ are captured.
  • Header lines (diff --git, index, --- a/, +++ b/, similarity index, rename from/to) are skipped because a hunk header match requires ^@@ - and content lines always carry a /-/+ prefix.
  • Empty and binary bodies yield zero hunks.

Review model & storage

Review/comment domain model, status state machine and per-review JSON storage, in packages/core/src/{review,store}.ts.

Decisions taken:

  • Immutable model. createReview, addComment, transition, resolveComment return a new Review; updatedAt is bumped by every op. now is injectable so tests are deterministic.
  • Comment anchors are on thread roots only. A root comment carries file/line/origin (sha + old line)/context (mandatory snapshot for the re-anchor fallback) and an optional suggestion (oldText→newText, V1 mandatory capability; empty newText = deletion). Replies link via parentId and keep anchors null — they belong to the thread, so re-anchoring only ever touches roots.
  • State machine (REVIEW_TRANSITIONS): open → request-changes → approved → merged → done; done reachable from any active state (terminable without merge), closed abandons (reopenable → open), merged only from approved. No self-transitions. Every transition is journalised in statusLog. Review status is per review, never per comment.
  • Resolve flips a comment to resolved with resolvedAt; allowed from active and detached (resolving a detached comment is the discard decision at merge time).
  • Storage: one JSON file per review (<id>.json) in a directory (.lopr/reviews). Atomic write (temp file + rename) so a crash never corrupts a review; schema version: 1 guarded by parseReview, which throws on malformed data — the store never returns null for a corrupted file.
  • IDs are path-safe: /^[A-Za-z0-9_-]+$/ enforced by the store on save/load, so an id can never escape the reviews directory.
  • Traps hit: TS casts Record<string, unknown> → Review fail without an as unknown hop; eslint flags _-prefixed unused vars even in destructuring-rest, so tests strip fields explicitly instead.

Anchoring engine

Re-anchoring a comment written on an old head onto a new head, in packages/core/src/anchoring.ts. This is the core of the software: comments must still mean something on the next agent iteration when the code moved.

Decisions taken:

  • Two-dot, tree-to-tree diff (getDiffBetween) — not the three-dot form. An agent routinely rebases/amends, so the mapping must compare the old head's tree to the new head's tree directly; --merge-base would silently compare an older base.
  • Re-anchor order: (a) exact hunk mapping (mapOldLineToNew) — context lines map positionally, a removed line returns null; (b) whitespace-tolerant context search (findContextWindow) when the line sits in a rewritten zone; (c) detached — never silent, never blocking alone. A deleted or binary file always detaches.
  • The snapshot is self-sufficient. The comment stores context (neighbouring lines including the anchored line) plus contextAnchor — the index of the anchored line in the snapshot. Without it the fallback could not locate the line from stored data alone, which is the whole point of the mandatory snapshot.
  • Whitespace tolerance collapses every whitespace run to a single space before comparing, so re-indented code still re-anchors; the anchored line itself is allowed to have changed (that is why the fallback triggers at all). The best window wins on match count, ties broken by proximity to the naively-shifted position.
  • Engine stays pure: new-side file contents arrive through an injected getNewLines adapter; newFileProvider (git show sha:path) is the production adapter, tests use stubs.
  • Traps hit: git error messages are locale-dependent — subprocesses now run with LC_ALL=C so showFile can recognise “path does not exist” and return null instead of throwing.

Review commands service

Orchestration layer, in packages/core/src/service.ts: a ReviewService tying the model, the store and the git gateway together behind one injected interface ({gateway, store, author?, cwd?, now?}). This is what the CLI/TUI will call; the domain stays pure and unaware of it.

Decisions taken:

  • Commands, not a repository: newReview, comment, resolve, transitions (approve/requestChanges/ close/done/generic transition), status, list, summary, reanchor. Every write goes through the domain helpers, reloads from the store, saves back — the store is the single source of truth, the service holds no cache.
  • Comment creation captures its origin: the head sha and the anchored line are frozen at creation time into origin, and the context snapshot is built live from git show head:path via newFileProvider. The snapshot is mandatory — re-anchoring later relies on it alone. Line validity (1..N, file exists) is enforced at creation, not at re-anchor time.
  • Re-anchor is a service-level, one-shot operation over every root comment: it diffs origin.sha → head per comment, applies the anchoring engine, and persists only when something moved. Replies are never touched; a comment already sitting at the head (origin.sha === head) skips the diff entirely (observable: zero gateway calls). A successful re-anchor clears detached, a failed one sets it. origin is immutable — it is the point the comment was born, re-anchoring only moves the volatile file/line/status.
  • Branches resolved per command: newReview uses resolveBranches (current branch + default branch) unless explicit baseBranch/headBranch are passed; the head sha is re-parsed on every re-anchor so the latest agent iteration is picked up.
  • Deterministic by construction: now() is injectable, so every timestamp in the model is a pure function of it — the service tests rely on this.
  • Traps hit: TS widens literal statuses across object spreads in the re-anchor map, producing string instead of the union — fixed by typing the callback as Promise<ReviewComment>. Test fixtures that fake git diff output must start with diff --git … or the body counter in assembleFiles rejects them.

REVIEW.md export

Renders a review as the stable REVIEW.md contract for the agent to ingest, in packages/core/src/export.ts (exportReviewMarkdown, pure Review → string) — surfaced through ReviewService.exportReview. This is the agent-facing output the apply-review skill will consume.

Decisions taken:

  • A stable, versioned contract: title + <!-- lopr-review: v1 --> machine marker, then metadata (id · base · head · status · author · updated). The format is a compatibility surface, so it is versioned independently of the review schema.
  • One thread per ###, grouped by file, ordered by line. The snippet is the stored context snapshot in a text fence with the anchored line prefixed > — the self-sufficient snapshot the anchoring engine already guarantees. Replies nest under their root (#### author — createdAt) with no snippet of their own.
  • Suggestions render as an actionable diff block (Apply in `path`:` + diff fence), so the skill can apply oldText→newText mechanically; an empty side of a suggestion renders an empty line rather than a phantom +/-.
  • Sections appear only when non-empty: Auto-resolved conflicts (driven by the conflicts log the merge orchestrator will fill), Feedback (active + resolved roots, resolved marked [resolved]), Non localized (detached roots — never silently dropped). An empty review is still a valid, parseable document.
  • The conflict log lives on the review, not in the exporter: schema bumped to version: 2 with conflicts: AutoResolvedConflict[] (path + at, validated by parseReview) and a domain op logConflict — the export is then a pure view of one object and the merge epic only appends records.
  • Traps hit: a for…of over Map with an unused key binding is flagged by eslint — iterate .values() instead. Backticks inside inline paths are escaped so a hostile path cannot break the fence.

Merge

Orchestrated merge of the reviewed branch into its base, in ReviewService.mergeReview with new gateway primitives in packages/core/src/gateway.ts.

Decisions taken:

  • Consent is a hard gate: mergeReview(id, { consent: true }) throws without it — the CLI/TUI ask the human first. Merging requires an approved review; the state machine still enforces approved → merged via transition.
  • --no-commit --no-ff, then the service commits. The gateway returns a MergeResult (clean / up-to-date / conflicts) instead of throwing on conflict, so the orchestrator decides. Non-conflict failures (e.g. unrelated histories) come back as failure with an empty conflict list; the service aborts best-effort and rethrows as a ReviewError — the repo is never left mid-merge.
  • Conflicts auto-resolve main-wins: resolveOurs does git checkout --ours -- path + git add per conflicted path; when ours has deleted the path (delete/modify), the checkout fails and the deletion wins via git rm -f. Each auto-resolution is journalised with logConflict — the REVIEW.md export already renders them.
  • Already up to date is not an error: when the head is already contained in the base, the merge is skipped but the review still moves to merged.
  • Cleanup is opt-in: cleanup: true deletes the head branch and removes the review file after a successful merge (the local single-contributor mode); the review is kept by default for the audit trail.
  • Branches are checked out by the orchestrator: the service switches to the base branch before merging, so a dirty worktree fails loudly at the checkout rather than corrupting a merge.
